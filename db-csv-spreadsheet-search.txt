app.post('/reserve', async (req, res) => {
  const { room_id, date, user_id, idempotency_key } = req.body;
  // Acquire lock (simple Redis lock)
  const lockKey = `lock:room:${room_id}:${date}`;
  const got = await redis.set(lockKey, "1", 'NX', 'EX', 10); // 10s lock
  if (!got) return res.status(409).json({ error: 'Room being reserved, try again' });

  try {
    // Double-check availability from service
    const curr = await getAvailability(date);
    if (!curr.find(r => r.id === room_id)) {
      return res.status(400).json({ error: 'No longer available' });
    }
    // Create booking via internal API with idempotency
    const booking = await axios.post('http://internal-service/api/bookings', {
       room_id, date, user_id, idempotency_key
    });
    res.json({ booking });
  } finally {
    await redis.del(lockKey);
  }
});

use Illuminate\Http\Request;
use Illuminate\Support\Facades\DB;
use App\Models\Room;
use App\Models\Booking;

public function reserve(Request $req)
{
    $roomId = $req->input('room_id');
    $date = $req->input('date');
    $userId = $req->user()->id;
    $idem = $req->input('idempotency_key');

    // Idempotency: if booking exists with same idempotency key, return it
    $existing = Booking::where('idempotency_key', $idem)->first();
    if ($existing) return response()->json($existing);

    return DB::transaction(function () use ($roomId, $date, $userId, $idem) {
        // lock room row
        $room = Room::where('id', $roomId)->lockForUpdate()->first();
        if (!$room || !$room->isAvailableOn($date)) {
            abort(400, 'Room not available');
        }
        // create booking
        $booking = Booking::create([
            'user_id' => $userId,
            'room_id' => $roomId,
            'date' => $date,
            'idempotency_key' => $idem,
            'status' => 'confirmed'
        ]);
        return response()->json($booking);
    });
}

organization_id — tenant scoping

text — short human-readable description plus aliases/paraphrases (this is what you embed)

aliases — optional list (also included in text or embedded separately)

source_type — "action" or "kb"

action — canonical name e.g. "CHECK_AVAILABILITY"

api_template — method/url template (no secrets)

params_template — placeholders to fill from user input

min_score_to_use — numeric threshold for auto-call

roles_allowed, version, last_updated, notes — useful ops fields

Do NOT store: API keys, DB credentials, raw SQL, or PII inside the vector DB.

Practical tips / patterns

Include aliases inside text (or create separate alias docs) — it boosts embedding match recall for many paraphrases without adding complexity.

Optionally embed aliases separately as additional points pointing to same action_id if you want extreme recall & faster reranking.

Keep text short (1–3 sentences + aliases). Large blobs hurt precision and cost.

Min_score: start 0.75–0.80 for auto-call; use 0.65–0.8 as “uncertain” band to trigger reranker/clarify.

Filter by organization_id at query time to avoid cross-tenant matches.

Log: store which document matched, its score, and the filled api_template for audit/debug.

Example runtime flow (quick)

Embed user query.

Search org collection → get top N points with payload.

If top.payload.source_type == 'action' and score >= min_score_to_use → extract params, fill api_template and call backend API.

Inject live response into LLM prompt and return natural language to user.

If score in uncertain band, rerank or ask clarifying Q.

Bottom line

Yes — keep an action doc in the vector DB (so semantic matching works). But store the executable bits (templates, endpoints) in metadata/payload and keep secrets out of the index. That gives you reliable matching without sacrificing safety or freshness.
